# vctrmemo — 利用形態の仕様案

**Status: DRAFT / 未承認。コード変更なし。採用前に仕様レビューが必要。**

## 確定している前提

- vctrmemoはNotion型の個人中心のノート・データベースアプリ。
- 1人で開始・利用できる。別アカウント、相手の参加、グループ作成は不要。
- 同じ人のスマホ・PC同期と、他人との共同編集は別機能。
- 共有は任意であり、知らないうちにデータを他人へ渡さない。
- 既存データを無断で消去・変換しない。

## 仕様案 1: 1人・1端末

- 端末内の個人ワークスペースでページ、ブロック、データベース、検索を使う。
- ローカル自動保存。通信できなくても編集可能。
- 共有・招待・チャット参加は一切要求しない。
- 共有操作をしなければ外部送信されず、チャットの変更履歴も混ぜない。

## 仕様案 2: 1人・複数端末

- 同じ本人のVectorアカウントに紐づく個人ワークスペースを複数端末で扱う。
- 編集を両方向に同期し、オフライン時は端末保存、復帰時は競合処理。
- 他人の招待、グループチャット、チャット全体への履歴配信は不要。
- 本人専用の同期経路と端末認証が成立するまでは、同期機能を完成と呼ばない。
- 端末を解除しても、元端末の内容は勝手に削除しない。

## 仕様案 3: 複数人

- 個人用とは別の共有範囲を設け、選択したページ・DBだけを対象にする。
- 相手のVector IDを指定して招待し、承諾されて初めて共有を開始する。
- 権限候補はOwner（管理）、Editor（編集）、Viewer（閲覧）。
- 非共有の親・子ページ・参照先DBは勝手に公開しない。
- 共有解除後は新しい更新へのアクセスを止める。既に保存された複製の回収は保証できない。
- 個人データと共有データは別の名前空間、保存、変更履歴に分ける。モード切替時にマージしない。

## 絶対に混同しないこと

- 2端末 = 2人ではない。
- チャット参加者 = 共同編集の権限所有者ではない。
- チャット更新を送ること = 本人用の同期ではない。
- 共有オフ = 過去に配信済みデータの回収ではない。
- 模擬テスト成功 = Vector実機の配送成功ではない。

## まだ確定していない設計判断

1. 既存の個人ページを同じIDのまま共有するか、独立した共有領域に移す／複製するか。
2. 子ページ・関連データベースをどの範囲まで共有対象に含めるか。
3. 同一アカウント2端末の同期経路と本人確認の実現可能性。
4. 暗号化、鍵の管理、端末解除・復旧の仕様。
5. 共同編集の詳細な権限と招待・取り消しの操作。

## 現行版の不一致

v0.11のチャット共有は、受け取った履歴を個人データへ統合するため、この提案の個人／共有の分離を満たさない。同一アカウントの複数端末同期も未実装。

## 実装を再開する条件

- この仕様案をレビューし、未決事項を確定する。
- 既存の保存データを保持する移行・復旧手順を作る。
- 1端末単独利用、同一本人2端末、招待した複数人をそれぞれ別々に試験する。
- 承認前に共有コードの設計変更を追加しない。

## 具体的な設計決定案（2026-10-22・未承認）

次の項目を提案として明文化する。**利用者の承認前に確定仕様として実装しない。**

### ワークスペースの3種類とデータ境界

| 種類 | 実体 | 閲覧できる人 | 変更履歴の格納先 |
| --- | --- | --- | --- |
| PERSONAL_LOCAL | 個人ワークスペースの端末内複製 | その端末の本人 | personalの履歴。初期状態は他所へ送らない |
| PERSONAL_SYNCED | 同じ個人ワークスペースの認証済み端末間複製 | 同一の本人だけ | personal専用の暗号化同期履歴 |
| SHARED | 明示的に共有へ移したページ／DBの作業領域 | 招待を承認し、権限が有効な参加者だけ | shared専用の暗号化履歴 |

1. 新規利用者は必ず PERSONAL_LOCAL から始める。2人目の利用者や、Vectorチャットへの投稿は必要ない。
2. PERSONAL_SYNCED は PERSONAL_LOCAL に本人専用の同期経路を追加するだけ。二人の共同編集ではない。
3. SHARED の閲覧は個人履歴とは別にする。個人領域の内容は共有履歴に無条件で統合しない。
4. 切り替え操作は表示領域の変更であり、**データのマージを意味しない**。共有権限の新規付与も行わない。

### 既存個人ページを共有する方法（推奨する選択）

**「共有する」を押すと、対象ページの現在内容を選択的に SHARED 領域へ移管する方式を提案する。** UIに「共有領域へ移す」と明示する。
- 最初にページ・含める子ページ・埋め込みDB・リンク先の候補を列挙し、共有対象を明示的に選ぶ。選ばれなかった対象は共有しない。
- 変更履歴を丸ごと公開せず、選択範囲の現在状態だけを新しい共有履歴の初期データにする。移管直前に個人用のローカルバックアップを作る。
- 同じ論理ページとして共同編集できる。個人エリアに編集可能な別コピーを無断で作らない。参照は権限を見て解決し、非共有の参照先は伏せる。
- SHARED領域内で編集した結果は、許可された全参加者で一致させる。相手の更新はpersonal履歴に書かない。
- 「共有を終了」すると他者のアクセスを取り消し、その時点の内容をpersonalへ戻す選択肢を提示する。既に相手に配送したデータを完全消去したとは言わない。
- **注意:** この移管方式は承認待ち。現在のv0.11のチャット共有は、これを実装したものではない。

### 画面挙動（受け入れ条件）

- 初期画面：**個人**と「この端末に保存」を表示。共有ボタンや招待操作は初期操作の妨げにしない。
- 端末同期未設定：「同期していません」と表示。同期済みや暗号化済みを偽装しない。
- 同一本人の2端末：1回だけ本人の端末認証を行い、以後は双方向自動同期。相手のVector IDは必要ない。
- 共有操作：「ページを共有」→対象範囲の選択→招待相手→閲覧／編集権限→確認→相手の承諾、の順。確認前には送信しない。
- 招待を受けた側：自分の個人領域に自動マージせず、別の「共有」セクションに表示。
- 解除時：共有セクションからアクセスを閉じ、個人領域を変えない。個人化して戻す場合は明示的な移管とする。
- 関係のある非公開ページやDB：タイトル・プロパティ・履歴を漏らさない。必要なら「アクセス権なし」と表示する。

### Vector公式資料と実証の境界

- WebXDCの sendUpdate は**アプリが属するチャットの全参加者向け**。個人専用同期ではない。
- WebXDCの selfAddr は**そのMini Appインスタンス内でのID**。異なるアプリ全体に通用する認証用IDとは扱わない。
- Vectorは本人の複数端末へ一部のアプリ設定や所属情報を同期する実装を公開している。しかしMini Appの個人データが同じ経路で扱えることは未実証。
- **設計候補:** 個人用の暗号化同期アダプタをVector SDKまたはNostrの本人向けイベントで実装。実機で暗号化・認証・重複排除・オフライン復旧を検証し、成立しない方式は採用しない。
- 外部の有料クラウド、サーバ常駐、2アカウント目を必須条件にしない。
- 公式参照: https://webxdc.org/docs/spec/sendUpdate.html
- 公式参照: https://webxdc.org/docs/spec/selfAddr_and_selfName.html
- Vector実装資料: https://github.com/VectorPrivacy/Vector/blob/master/docs/concord/README.md
- Vectorリリース: https://github.com/VectorPrivacy/Vector/releases

### 実装の順番（設計承認後）

1. **データ保護:** v0.11以前のローカルバックアップ、personal/shared分離、読み取り互換、旧共有モードの安全な無効化。個人履歴の変更なしをテスト。
2. **本人2端末:** Vector SDK/ホストの同期経路を検査し、本人以外に送れないことと2端末で同じ内容になることを実機テスト。
3. **任意の共同編集:** ページ単位で移管・招待・承諾・Viewer/Editor/Owner・拒否・解除を実装。個人データ漏えいテストを必須にする。
4. **安定化:** 破損・中断・端末紛失・競合・復元を実測してから完成扱いにする。
